# 海外工具网站国际化（i18n）方案

本文档将多语言建设的目标、URL 策略、SEO 要求、工程扩展与分阶段落地整理为可执行约定，供与 [1-海外工具网站项目调研与实施方案](./1-海外工具网站项目调研与实施方案.md)、[2-海外工具网站落地方案](./2-海外工具网站落地方案.md) 配套使用。

**当前阶段结论（已讨论确定）：**

- **默认语言：英文（`en`）** — 与「海外流量 + 英文 SEO」主战略一致。
- **第二语言：简体中文（建议语言标签 `zh-CN`）** — 面向中文读者或运营需要时使用；若未来明确港澳台/繁体，可再拆 `zh-TW` 等，见下文「地区与语言变体」。
- **路由形态：路径前缀（locale segment）** — 如 `/en/...`、`/zh-CN/...`（具体是否省略默认语言前缀见「URL 与路由策略」）。
- **扩展性：按多语言产品设计** — 文案外置、语言列表配置化，便于后续增加日语、西班牙语等而少改架构。

---

## 一、方案目标与非目标

### 1.1 目标

| 维度 | 说明 |
|------|------|
| 用户体验 | 用户可通过站内切换或直达链接访问对应语言；`html lang`、基础无障碍与阅读体验正确。 |
| SEO | 各语言有**独立可索引 URL**；`hreflang` / `canonical` / sitemap 与抓取策略一致、可维护。 |
| 推广 | 投放、外链、社媒分享可携带**明确语言版本的落地 URL**，便于归因与 A/B。 |
| 工程 | 新增一种语言以「加配置 + 加翻译文件 + 路由接入」为主，避免大改目录与组件树。 |

### 1.2 非目标（本阶段可不实现）

- 自动根据 IP/浏览器语言**强跳**语言（易干扰抓取与用户预期，见「禁忌」）。
- 同一 URL 下用 Cookie 切换语言且**无独立 URL**（不利于 hreflang 与分享；若仅作内部工具可另议，与本方案推荐路径不一致）。
- 机器翻译流水线、翻译 TMS 对接（可作为后续工具链，本文只约定内容存放与发布规则）。

## 二、URL 与路由策略

### 2.1 推荐形态：路径前缀

所有面向用户的页面位于**带 locale 前缀**的路径下，例如：

- 英文：`https://example.com/en/tools`、`https://example.com/en/json-formatter`
- 中文：`https://example.com/zh-CN/tools`、`https://example.com/zh-CN/json-formatter`

**语言标签**建议使用 **BCP 47**（如 `en`、`zh-CN`），与 `hreflang`、HTML `lang` 一致。

### 2.2 默认语言与根路径 `/`

两种常见做法，**选一种全站坚持**：

| 策略 | 做法 | 优点 | 注意 |
|------|------|------|------|
| A. 根路径即默认语 | `/` 渲染英文首页；其他语言必须带前缀 | URL 短、品牌主站感强 | 需在文档与实现里写清：`/` 与 `/en` 是否 **301 合并**（避免重复内容） |
| B. 全部带前缀 | `/` **301 → `/en`**（或到 `defaultLocale`） | 规则最单一、多语言对称 | 英文也多一段路径 |

**建议：** 若长期以英文为主品牌入口，可采用 **A**，并对 `/en` 与 `/` 做 **canonical 统一**（择一为主，另一 301 或 canonical 指向主 URL），避免两套首页抢权重。

### 2.3 站内链接

- 所有导航、工具互链、sitemap 中的 URL **必须带当前 locale**，或经统一 helper 生成，禁止大量硬编码无 locale 的路径。
- 语言切换组件：跳转到**同一路由的另一 locale**（路径结构镜像），而非仅改 Cookie。

## 三、技术选型与工程结构（Next.js App Router）

### 3.1 推荐库：`next-intl`

与 **Next.js App Router** 配合成熟，支持：

- 中间件中的 locale 检测与重定向（与上文策略对齐配置即可）
- 服务端 / 客户端组件中的 `useTranslations` 等
- 与 `generateMetadata` 结合做多语言 title/description

（具体 API 以官方文档为准；落地时在 `web/` 内接入即可。）

### 3.2 单一事实来源：`locales` 配置

在代码中维护例如：

```ts
// 示例，非最终实现
export const locales = ['en', 'zh-CN'] as const;
export type Locale = (typeof locales)[number];
export const defaultLocale: Locale = 'en';
```

**后续加语言**：仅扩展 `locales` 数组、增加 `messages/{locale}.json`（或等价文件），并同步 SEO 与 sitemap 生成逻辑。**禁止**在业务组件里散落 `'en' | 'zh-CN'` 字符串而不读配置。

### 3.3 文案外置与键名规范

| 约定 | 说明 |
|------|------|
| 存放 | 如 `messages/en.json`、`messages/zh-CN.json`；语言多时按 namespace 拆文件（如 `common`、`tools`、`legal`）亦可。 |
| 键名 | 使用**稳定英文路径式 key**（如 `tools.jsonFormatter.title`），**不要用**某语言整句当 key。 |
| 缺键 | CI 或脚本对比 `en` 与 `zh-CN` 键集合，避免上线后裸漏 key。 |
| 长文案 | 隐私政策、条款等可单独文件或 CMS，但仍应对应到 locale 路由下页面。 |

### 3.4 组件与 Metadata

- **UI 字符串**：尽量来自 `t('...')`；数字、日期格式可用 `Intl` 或库按 locale 格式化。
- **`metadata` / Open Graph**：按 locale 生成 `title`、`description`、`openGraph.locale`；`canonical` 指向**当前语言页自身 URL**。
- **`html lang`**：`en` 与 `zh-CN` 分别设置，勿写死 `en` 全站。

### 3.5 RTL（从右到左）预留

当前中英为 LTR。若未来增加 **ar、he** 等：

- 根元素 `dir="ltr" | "rtl"` 随 locale 切换。
- 样式优先使用 **逻辑属性**（如 `margin-inline-start` / Tailwind 的 `ms-`、`me-`），减少硬编码 `ml-`/`mr-`，降低 RTL 改造成本。

## 四、SEO 实施清单（必须对齐）

### 4.1 `hreflang`

对每个「成组」的页面（同一工具、同一首页等），在 HTML `<head>`（或 HTTP Header / sitemap，择一或组合）中声明：

- 当前页语言
- 所有**已提供翻译版本**的替代 URL
- **`x-default`**：一般指向**默认语言**（英文）的 URL，便于未匹配到具体语言时给搜索引擎默认版本

**注意：** `hreflang` 只应列出**真实存在且内容对应**的 URL；不要链向空页、404 或错误语言版本。

### 4.2 `canonical`

- 每个语言版本 **canonical 指向自己**。
- 避免跨语言 canonical 聚合到单一 URL（除非有明确的单一权威 URL 策略且已评估重复内容风险）。

### 4.3 Sitemap

- 为**每个已上线的 locale** 生成可抓取 URL（可一个 sitemap 内多语言，或分文件 + sitemap index）。
- 新语言上线：整站该语言下重要路径应进入 sitemap，并在 Search Console 中可按属性/规则监控。

### 4.4 结构化数据（JSON-LD）

工具页的 `WebApplication` / `SoftwareApplication` 等：

- `name`、`description` 与**当前页面语言**一致。
- `url` 为当前 locale 的绝对地址。

### 4.5 重复内容与不索引策略

- **`/` 与 `/en` 并存时**：必须处理 canonical 或 301，避免双首页。
- **某语言暂未翻译某页**：见下一节「未翻译内容策略」，全站统一一种规则。

## 五、未翻译内容策略（上线前必须选定）

新增第三种及以上语言时必然出现「部分页面未译」的情况，**三选一，全站一致**：

| 策略 | 行为 | SEO 与体验 |
|------|------|------------|
| **A. 404** | 该语言下无此路径 | 清晰；外链需注意不要指向不存在路径 |
| **B. noindex** | 页面存在但标注不索引 | 需避免与 hreflang 互链冲突（一般不向 noindex 页发 hreflang） |
| **C. Fallback 到默认语言** | 显示英文内容，URL 仍为该 locale | 易有「URL 与内容语言不一致」风险；若采用须在页面显著标明或调整 hreflang 策略，慎用 |

**建议：** 工具站页面数量大时，优先 **A 或 B**；若用 **C**，需产品 + SEO 专项评审。

## 六、扩展更多语言时的检查表

在 `locales` 中增加新代码（如 `ja`、`es`）时，至少完成：

1. 新增 `messages/{locale}.json`（或 namespace），并与 `en` 键集对齐或记录允许缺省键。
2. 中间件 / 路由表包含新 locale。
3. Sitemap 包含新 locale 下应索引的 URL。
4. 页面级 `hreflang` 更新为「全量已上线语言」集合。
5. Search Console：视是否使用独立属性/目录监控决定配置方式。
6. 法务：Privacy / Terms 是否提供该语言版本（若有法律要求）。
7. 字体与排版：东亚、西里尔、阿拉伯等字符集与行高检查。

### 6.1 地区与语言变体

- **宽码**：`es` 覆盖多国的泛化版本。  
- **细码**：`es-MX`、`pt-BR` — 适合投放与本地化 SEO 深做时。  
- 路径前缀可与语言码一致，避免同一内容多 URL 无 `hreflang` 互链。

## 七、推广、分析与合规

| 领域 | 建议 |
|------|------|
| 投放 | 英文广告落地 `/en/...`；中文落地 `/zh-CN/...`，与 hreflang 一致。 |
| GA4 | 用 URL 段或自定义维度区分语言，避免全站流量混读。 |
| Cookie 同意 / 广告 | 多语言下同意横幅与政策链接指向**对应语言的法律页**（若已翻译）。 |
| 品牌 | 路径前缀不替代域名策略；海外主站仍以 `.com` + 英文为主符合现有调研结论。 |

---

## 八、禁忌与常见错误

1. **仅按 IP 或浏览器语言做强制 302 跳转** — 干扰 Googlebot 与用户，且易造成错误索引。  
2. **同一 URL 多语言 HTML 混出** — 不利于 hreflang 与分享。  
3. **大量机器翻译、无差异的镜像页** — 易被判定为低价值重复；至少标题、首段、FAQ 等做本地化。  
4. **hreflang 与 canonical 互相矛盾** — 上线前用抓取工具或 Rich Results / 国际定位检测抽查。  
5. **忘记更新 sitemap** — 新语言整树未提交可发现率低。

## 九、与《落地方案》的衔接

| 落地方案模块 | 国际化后的调整要点 |
|--------------|-------------------|
| 第 0 周 前端骨架 | `app/[locale]/...`（或库推荐目录）；中间件；`messages` 目录。 |
| SEO 基础 | `metadata` / `sitemap` / `robots` 按 locale 生成；根路径与默认语规则写死。 |
| 每工具页产出物 | Title/H1/Description/JSON-LD 均走翻译；URL 带 `en` / `zh-CN`。 |
| 指标与周节奏 | Search Console 可按目录拆分英文/中文表现。 |

## 十、建议落地阶段（工程）

| 阶段 | 内容 |
|------|------|
| **Phase 0** | 锁定 URL 策略（`/` vs `/en`）、选定 `zh-CN` 是否带地区后缀；文档评审。 |
| **Phase 1** | 接入 `next-intl`（或等价方案）；迁移 `Header`/`Footer`/首页/`/tools` 与 1～2 个工具页验证链路。 |
| **Phase 2** | 全站页面迁移文案；`generateMetadata` + JSON-LD 多语言；语言切换组件。 |
| **Phase 3** | `hreflang` + sitemap + canonical 全量；Search Console 验证与抽样测试。 |
| **Phase 4** | 缺键检测、术语表；预留 RTL 与第三语言的配置与文档更新流程。 |
